# Architecture

One repository supports two delivery paths. `.github/workflows/release.yml` gates Windows installer/portable publication on native tests and the reusable Ubuntu `relay.yml` container acceptance job. Each release carries an exact-commit source archive, gateway source package, provenance receipt and SHA256 checksums; reruns cannot move existing tags. Coolify builds the independent gateway image from `compose.relay.yaml`. It generates/persists `SERVICE_HEX_64_WARAQDB`, which both services reuse; PostgreSQL DNS, health dependency, persistent volume and schema initialization are supplied by Compose and the gateway entrypoint. Initial Git access/domain routing and desktop/phone pairing remain explicit setup. See `README.md` for the repository map and both delivery flows.

The native Qt Quick/QML UI talks to a QObject bridge. The bridge runs source discovery off the GUI thread and presents snapshots of durable state. SQLite WAL transactions serialize task claims. A scheduler owns one download slot plus independent Deepgram and OpenCode worker pools. Each worker has at most one active job and a private cancellation event.

Queue aggregates and selection use a native JavaScript array parsed from cached `Bridge.jobsJson`, invalidated only by `jobsChanged`. Iterating a Python QVariantList from QML repeatedly reads/converts the entire sequence and can stall large queues. Worker elapsed-time and log-only refreshes do not invalidate the queue snapshot. The visible list still uses `jobsModel` for in-place row updates and stable scrolling.

Bulk queue deletion takes the scheduler lock before the store lock, matching dispatch. It removes idle job/stage rows in one transaction while retaining events, source files, workspaces and library copies. An active worker protects its job until publication/finally completes, even after its stage becomes completed; retry uses the same guard. Cancellation holds the dispatch lock throughout stage-state changes. Worker preparation/start failures become visible failures and release their active slot. The bridge retains all stages for durable dependency logic, while imported TXT rows expose only the Word step to QML.

Internet access uses an operator-owned gateway, deployed with `compose.relay.yaml` and `deploy/relay/Dockerfile`. `relay/` is an independent FastAPI/SQLAlchemy service with PostgreSQL, a single ASGI worker and device-scoped routing. A desktop enrolls with a short-lived single-use operator code, stores its credential in Windows Credential Manager, and makes an outbound authenticated WSS connection. There are no inbound desktop ports for Internet mode. The gateway terminates TLS and is a trusted data intermediary; this is not end-to-end encryption.

`internet.py` marshals allowlisted requests onto Qt with cancellation, connection generations, deadlines and a persistent mutation journal. Disconnected requests are not replayed. One-time pairing tickets require explicit desktop approval of a phone claim and matching code. Durable phone grants are checked against the exact device on every action and download; revocation cancels outstanding requests. One browser may hold separate grants for several explicitly paired devices. The browser fixes its current device for the document lifetime and navigates fully when switching. Sessions use Secure/HttpOnly/SameSite cookies; the gateway checks canonical Host, Origin and mutation headers. Upload admission and JSON sizes are bounded; downloads stream bounded chunks. Identity files and the replay journal are excluded from settings exports and deployment build context. Internet access starts only when requested and does not stop the scheduler when disconnected.

`remote_commands.py` is the shared GUI-thread command implementation for LAN and Internet. Each transport owns a separate instance for source discovery/selection; both operate the same live Bridge and scheduler. `remote_common.py` contains shared limits and errors. `mobile/` serves both modes, detecting the gateway through bootstrap while keeping LAN authentication separate. See `deploy/relay/README_AR.md` for deployment and recovery.

Managed ChatGPT accounts are opt-in and use the existing OpenCode 2 binary. `opencode_accounts.py` stores non-secret identity fingerprints, aliases, priority, cooldowns and per-attempt audit in the task database. The scheduler resolves the exact saved worker plus the session override at claim time, leases a suitable account under the scheduler/store lock order, and preserves that choice through execution. Sticky selection stays on the same eligible account, including when its configured concurrency is full. A confirmed quota event parks that account and lets subsequent attempts choose the next eligible one; quota waits do not consume an ordinary job failure budget.

Quota visibility is separate from execution routing. `opencode_usage.py` validates and allowlists service-backed windows; duration, not primary/secondary position, identifies the five-hour and weekly counters. `account_usage.py` coalesces per-account requests into at most two background readers, observes polling/backoff limits and emits normalized results for queued application by the Qt bridge. The GUI refresh and authenticated phone state snapshots read cached data only. A latest-only `chatgpt_usage` table retains the last successful snapshot and attempt timing; account authentication epochs and request IDs reject results after deletion, reauthorization or a newer request. Execution `generation` retains its existing arbitration purpose. Zero remaining is distinct from a missing window; cache age, restart and elapsed reset timestamps require a fresh reading rather than fabricated replenishment.

The runtime is the only quota component that handles native credentials. Its fixed HTTPS GET targets the legacy Codex usage route with TLS verification, no redirects, no ambient proxy, bounded response size and bounded waits. The legacy browser/device methods and tested native version are capability-gated; dynamic `chatgpt-token-sharing` credentials are not sent to that route. Native credential bodies and access tokens stay in private runtime-side Python operations and never enter settings, usage rows, GUI signals or phone responses. OpenCode continues to own token renewal. Quota read failures do not become account execution failures or alter routing/cooldowns/holds.

Expiry-related renewal may restart an idle native account process only under a scheduler maintenance reservation. Lock order is scheduler then store; no network/process wait occurs while holding either. A published execution lease already counts as busy before its session exists. Restart additionally requires valid empty native activity, no tracked sessions and proof of the old process's termination. Account lifecycle guards prevent concurrent session creation/removal or a second owner; closure invalidates pending work and forbids new startup. A temporary maintenance reservation preserves sticky account selection rather than rotating merely to read telemetry. The phone receives a separate allowlisted summary with session-local display keys, aliases, counters and times, without native IDs, email or authentication material.

`opencode_runtime.py` supervises one native `serve --stdio` process per account on an authenticated loopback endpoint, with isolated XDG data/state/cache/config directories. OpenCode owns OAuth storage and refresh; Waraq never stores its tokens in task settings. OAuth is user initiated and marshalled back onto Qt through generation-checked signals. Worker runs pre-create native sessions with explicit task locations and per-session tool environments, including PWD and skill NODE_PATH. Untrusted inherited API credentials and OpenCode database/config overrides are removed from this mode. Each managed attempt writes to its own workspace; a final document is adopted only after session inactivity, TXT hash and DOCX validation. Cancellation interrupts and checks the actual server session; an unproven stop creates a durable replay hold rather than allowing a second execution. Remote snapshots expose only the account alias, status and next check time.

Modules:

The gateway enforces one phone grant per device with a unique database index. Pairing reservations, approval and collection share the device lock; a replacement requires explicit revocation of the current phone. Expired/idle grants can release the slot. Schema initialization upgrades the index safely and refuses legacy duplicate grants without deleting them. Different people enroll their own desktops through operator-issued codes and approve their own phones; there is no separate multi-user account portal. Deployment instructions are customized for `waraqstudio.jadallah.work` and the user's reported Coolify v4.4.6 in `deploy/relay/COOLIFY_SETUP_AR.md`; that Coolify instance has not been exercised locally.

- `config.py`: validated non-secret settings, atomic writes, Windows credential-store integration, one-time worker-pool migration and explicit legacy import.
- `store.py`: tasks, stages, events and metadata cache; atomic claims and crash recovery.
- `services.py`: serialized YouTube access, speech normalization, Deepgram response/chunk persistence, isolated OpenCode execution, DOCX validation.
- `scheduler.py`: dependency/order gates, per-project concurrency, downstream queue/disk backpressure and worker lifecycle.
- `library.py`: subject/type-grouped mirror of finished artifacts, Word export, and a stable name manifest.
- `bridge.py`: UI operations and background discovery; no paid requests on startup.
- `remote.py` and `mobile/`: opt-in IPv4 LAN control of this Bridge, using Flask with Waitress's Windows-compatible WSGI server and bundled, offline HTML/CSS/JS. The desktop shows local interface URLs, an SVG QR with no credentials, and an eight-digit pairing code that expires in ten minutes. Opaque, memory-only 12-hour sessions use HttpOnly/SameSite=Strict cookies. Code renewal, stop, and process exit revoke sessions; no server starts automatically. Private/link-local/loopback peer and Host allowlists, same-origin checks, JSON/custom-header mutations, bounded bodies/connections and per-peer/global pairing throttles constrain LAN exposure. HTTP is explicitly scoped to a trusted LAN, with no public tunnel or port-forwarding setup.

Remote HTTP workers marshal allowlisted commands using a queued Qt signal and a cancellable Future; all Bridge/model/queue operations execute on the GUI thread. A request that times out before GUI dispatch is cancelled and cannot execute later, and queued requests re-check their session and server generation. Waitress's I/O loop has its own map and stoppable thread; shutdown cancels pending Futures, closes sockets and joins the dispatcher without starting another scheduler or recovering the live database. Failed binds clean up the dispatcher/map. Read snapshots expose an explicit field allowlist without configs, prompt bodies, credentials or filesystem paths. Downloads resolve only registered document/transcript paths under the task directory. TXT uploads validate all names/content before importing managed byte-preserving copies using the existing bridge import path. Mobile YouTube discovery has separate selection state, shares the existing YouTube gate/cooldown, and uses a consumable revision to reject stale/double enqueue. It participates in the desktop close/auto-stop busy guards. The web client polls without overlapping requests, retains form selections and keyed queue rows, suspends polling while hidden, disables mutations offline, and never automatically retries a mutation.
- `app_update.py`: stable GitHub installer lookup, numeric version comparison, optional per-user credential-store token for private releases, streamed/cancellable download, exact size and GitHub SHA256 digest verification, and atomic commit under the user data directory. The bridge marshals progress/results onto the GUI thread; install re-verifies the file, requires a paused/drained queue, launches Windows elevation and quits. CI stamps `_build_version.txt` into the frozen package and asserts its version in the executable environment smoke test.
- `models.py`: `DictListModel`, a QAbstractListModel over dicts that syncs rows in place (dataChanged / row insert / row remove) instead of the wholesale QVariantList republishing that used to reset every QML ListView to the top. Each model exposes a reserved `row` role holding the whole row dict; delegates read `row.<key>` so a data key (a worker's own `model` field) can never shadow the delegate's `model` wrapper.
- `qml/`: native screens and reusable controls. Data lists bind to bridge models (`jobsModel`, `workersModel`, `sourceModel`, `resultsModel`, `filesModel`, `providersModel`) so progress ticks, log lines and worker elapsed seconds update rows in place and never disturb the scroll position. Fonts and control metrics scale through `ui_scale` (0.8–1.4, live-applied from Settings) via a shared `fs()` helper and a `uiScale` property on the button/field primitives; `ui_compact` shrinks list rows, paddings and gaps through the `rh()`/`rs()`/`density` helpers; `ui_rail_collapsed` persists the collapsible navigation rail.

Task stage states: pending → running → completed. Terminal/action states: failed, blocked, uncertain, cancelled. Paused is used for local operations interrupted by process exit. Skipped stages count as dependency-satisfied only for valid plans. Claims compare-and-set `pending` under a database lock so two workers cannot execute the same stage. A transient failure returns a stage to pending with a future `next_retry` (deferral); the claim predicate honors that timestamp, so scheduled retries survive restarts and resume without user action. `retries` counts consecutive automatic deferrals of the current episode and resets on any explicit transition, success, or manual retry.

Service availability is split from job state: `manual_paused_stages` is set only by the user's pause button, while `automatic_stage_blocks` records an automatic guard (rejected cookies, low disk space) with its reason; `tick()` honours both, but only a user action lifts the manual one, while `Bridge.retry()`/`recheckStage()` lift the automatic one and requeue the jobs it parked — never the user's pause and never the rate-limit cooldown. The download worker row surfaces the automatic block reason through its error slot plus a `cooldownSeconds` countdown.

Automatic retry policy by `(stage, kind)`: YouTube download errors are classified by `Youtube.classify()` into `rate_limited` (429 — persists a shared cooldown into the `runtime_state` table so it survives restarts, defers the job to after the cooldown honoring `Retry-After` when present, budget `youtube_retry_attempts`), `failed` (network/server errors and anything unrecognised — escalating 5/15/45 minute deferrals, budget `youtube_retry_attempts`), `blocked` (cookies/login/age/403 — terminal for the job plus an automatic download-stage block), and `permanent` (deleted/private/geo/copyright/404 — one terminal failure with no retry and no service-wide stop). OpenCode `failed` outcomes keep the `auto_retry_attempts` budget, and its subscription-quota stops are classified from the provider's streamed error event (HTTP 429 / "usage limit has been reached"), not the exit code, and defer hourly up to `opencode_limit_retries` before a terminal failure that names the likely weekly limit. Deepgram explicitly rejected retryable HTTP requests are deferred to two distinct keyed backup workers, with 30/90 second delays after in-request retries; `uncertain` always requires a user decision.

The `runtime_state` table (key/value JSON in the same SQLite database) holds operational state that must survive a process restart, currently the YouTube cooldown deadline; it is read when the Youtube service is constructed and cleared lazily once expired, so a restart can never burst fresh requests while a persisted cooldown is still running.

Settings are snapshotted at enqueue. Worker model/language/agent parameters follow that snapshot; repaired credentials and executable/cookie paths apply to waiting jobs. Pool membership and worker enabled state apply immediately to future dispatch. Explicit reprocessing creates a new revision fingerprint and retains prior artifacts. Prompt templates are ordinary validated settings (`opencode_templates`): the selected template's text and name are snapshotted into the job's prompt at enqueue, so the revision fingerprint distinguishes templates and later template edits never rewrite queued jobs.

OpenCode workers carry a provider: `login` uses the credentials OpenCode already holds and its shared data directories, while every key-based provider (built-in OpenRouter, OpenAI API, Anthropic or Google, or a provider the user defines with its own environment variable) is fed a per-worker credential named `worker:provider` from the OS store and runs with `XDG_DATA_HOME`/`XDG_STATE_HOME` pointed at its own directory under `opencode_data_root`. That keeps five parallel runs off OpenCode's shared SQLite database and off the login directory, and the legacy auto-update-disable flag is retained for V1 workers. The model id is composed as `provider/model` unless it already carries the prefix; `login` models pass through as typed. An empty `variant` adds no reasoning override, because reasoning effort is provider specific. A key-based worker without a stored credential is parked with an explicit message instead of consuming a job. A session-only queue override can force one provider, model and reasoning level on every OpenCode worker regardless of its own configuration; it is not persisted, is refused for unknown providers, applies to the next dispatch, and an empty forced model falls back to the worker's own model composed with the forced provider — so the worker list and the dispatch always agree on what will run. The provider catalog is code-level for the built-ins plus `opencode_providers` for user-defined ones; a provider in use cannot be deleted.

A one-time migration normalises the pools: it removes the OpenRouter workers an earlier release created automatically (matched by id, provider and name together, so a hand-made worker is never touched) and tops both pools up to five workers by cloning the first saved worker, preserving the settings already in use. A worker the user deletes afterwards is never resurrected.

The library mirrors finished artifacts into optional subject folders and then `Word`, `التفريغات` and `الصوت` folders under `library_root`. Uncategorized jobs remain in the three top-level type folders. `folders` and `jobs.folder_id` are migrated in place; original job workspaces never move. A manifest pins the relative path chosen for each (job, kind) pair; old filename-only entries migrate when republished. Reassigning a job moves its mirror copy. Publishing copies after each completed stage, is idempotent by size and timestamp, is skipped when `library_auto` is off, and can never fail a stage. Explicit Word export writes stable per-job names under the same subject/type layout. Deletion is confined to library type folders under the root or one subject.

YouTube uses bundled `yt-dlp[default]` until the user installs an official stable Windows executable from Settings. The updater downloads the release executable and published SHA-256 sums, verifies the file and its version, then atomically replaces the data-directory copy under the YouTube gate. Later requests use the executable through a CLI adapter; an existing binary is not modified on failed verification. Source builds remain reproducible with the pinned package and compatible EJS optional dependency.

The bridge can arm a session-only auto-stop: when no stage is pending or running, no worker is active, and no discovery is in flight, it logs queue completion and quits through the normal shutdown path. Deferred, paused, blocked, or otherwise pending work always keeps the application open.

Deepgram commits raw responses before parsing and before honoring cancellation. Chunk responses are individually durable; a manifest marks completed audio segmentation. Lost network responses are uncertain rather than blindly retried. This reduces duplicate billing but cannot provide exactly-once external execution.

OpenCode discovery follows PATH and common per-user installation directories, unwraps known npm package layouts without executing shims, and accepts explicit native binaries. Explicit broken paths do not silently fall back to a different install. A bounded version probe is shared between workers, cached by resolved path/mtime/size, and invalidated when the binary is replaced. Supported major versions are 1 and 2; unknown versions fail before submitting a prompt. The environment check reports both path and version.

OpenCode 2 runs and model-list queries use `--standalone` so each child server inherits the intended environment rather than reusing the user's background service. V2 runs select reasoning with `provider/model#variant`, set both cwd and PWD to the task directory, and use `--auto` for noninteractive permissions while retaining explicit denies. V1 keeps `--dir` and `--variant`. Prompts follow the `--` argument separator. Key-based workers retain separate XDG data/state directories and discard an inherited OPENCODE_DB override that could defeat isolation; login workers retain the user's credential directories. HTTP quota detection accepts V1's error.data.statusCode and V2's error.status.

OpenCode works in a separate directory per task revision that receives a copy of the transcript; the prompt carries that copy's path plus the exact target DOCX path. The original TXT stays outside the working directory, and its hash is independently verified after the run. Success requires process exit success, a valid editable DOCX, and an unchanged original hash. This is isolation of working files, not an OS security sandbox; OpenCode retains the account permissions granted by its own configuration, and a rejected permission is reported as a dedicated failure.

Known product limits are documented in README_AR.md. Native integration and scheduler tests use temporary directories and service doubles; external provider availability and actual formatting require live acceptance testing.

Local transcript imports use file selection, a non-recursive folder scan with natural filename ordering, or a window-wide QML DropArea. The bridge validates UTF-8/BOM content and deduplicates canonical paths within the import, then submits valid files as a single ordered batch with the selected prompt template and subject folder. Store.add supports per-item input paths and writes a byte-preserving TXT copy into each new task folder within the batch transaction before publishing the job; failed batches roll back jobs and clean up newly created copies. input_path retains source provenance, while transcript points to the managed copy. Download and Deepgram are skipped, so scheduler dispatch begins at OpenCode and no longer depends on the external source file.
