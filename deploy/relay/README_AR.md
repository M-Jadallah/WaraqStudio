# نشر بوابة ورق على VPS بواسطة Coolify

تاريخ مراجعة الدليل: 15 أكتوبر 2026. هذا الدليل يطابق `compose.relay.yaml` والكود المرفق. لم يُنشر مورد على خادمك، ولم تُعدّل سجلات DNS. يتضمن المستودع فحص Docker Compose وPostgreSQL على Ubuntu في `.github/workflows/relay.yml`، وتستدعيه CI وبوابة نشر الإصدارات؛ راجع نتيجة تشغيله للالتزام المطلوب. تبقى اختبارات القبول على VPS أدناه ضرورية.

## ما الذي ستنشره؟

إعداد المستخدم: Coolify **v4.4.6**، والدومين **waraqstudio.jadallah.work**. لتنفيذ النشر بنفسك ابدأ من [الخطوات المخصصة](COOLIFY_SETUP_AR.md). التوافق مع إعدادات Docker Compose موضح وفق توثيق Coolify الحالي؛ لم تُختبر لوحة المستخدم فعليًا هنا.

يتكامل هذا الجزء مع تطبيق Windows في المستودع نفسه؛ راجع [الدليل الرئيسي](../../README.md) للفصل بين مسار بناء Windows ومسار نشر الخادم. يُنشئ Compose خدمتين فقط: `gateway` لواجهة الهاتف وقنوات الأجهزة، و`postgres` للهويات وبصمات الاعتمادات والاقترانات. تنشئ خطوة داخل مدخل `gateway` مخطط القاعدة قبل تشغيل HTTP؛ ليست حاوية ثالثة. تبقى المعالجة ومفاتيح الخدمات والملفات الأصلية في الكمبيوتر؛ يمر محتوى الأوامر والملفات عبر البوابة عند النقل دون أرشفته عليها.

كل نسخة ورق تحصل على هوية مستقلة. اقتران الهاتف بالجهاز A لا يمنحه صلاحية للجهاز B. يمكن للمتصفح نفسه الاقتران بأجهزة أخرى بخطوة مستقلة لكل جهاز، ثم اختيار الجهاز من قائمة واضحة.

الخادم يستقبل أجهزة أشخاص متعددين، لكن **هاتفًا واحدًا لكل جهاز**. لا يحتاج الأشخاص إلى حساب Coolify؛ يحصل كل منهم على رمز تسجيل خاص، ويوافق على الاقتران من الكمبيوتر نفسه. لا توجد بوابة حسابات مستخدمين مستقلة. لربط هاتف بديل يجب إلغاء الحالي أولًا؛ يُرفض أي اقتران ثانٍ أو موافقة متعارضة دون استبدال صامت.

الكمبيوتر يبدأ اتصال WSS صادرًا إلى الدومين عبر 443. لا يلزم فتح منفذ وارد على الكمبيوتر أو تغيير الراوتر. يجب إبقاء الكمبيوتر مستيقظًا وورق مفتوحًا، وتفعيل اتصال الإنترنت داخل ورق بعد كل تشغيل.

## 1. الدومين وإعداد الشبكة

اختر اسمًا فرعيًا مخصصًا مثل `waraqstudio.jadallah.work`. أنشئ سجل A إلى عنوان VPS؛ أضف AAAA فقط إذا كان IPv6 يعمل إلى الخادم فعلًا. تحقق من انتهاء انتشار DNS. يجب وصول 80 و443 إلى وكيل Coolify، وأن يحصل الدومين على شهادة صحيحة. يشرح [توثيق Coolify للدومينات](https://coolify.io/docs/core/networking/domains) إعداد DNS وHTTPS وتوجيه الطلبات إلى منفذ الحاوية.

إذا كان لديك CDN أو وكيل إضافي، تحقق من دعمه WebSocket وحدود الرفع والمهل. يمكن بدء الاختبار دون الوكيل الإضافي لتحديد مصدر الأعطال، ثم تفعيله والتحقق مجددًا. لا تعطل التحقق من شهادات TLS في ورق.

## 2. إنشاء مورد Coolify من Git

يجب أن يحتوي مصدر Git المختار على التغييرات وملف Compose، وأن يملك Coolify صلاحية قراءته؛ لا يكفي وجود الملفات على جهاز التطوير. استخدم مستودع ورق الكامل مباشرة، أو محتويات `WaraqGateway-Coolify.zip` من الإصدار بعد رفعها إلى مستودع خاص مستقل. الحزمة الثانية مصدر قابل للبناء، وليست صورة Docker. لا يلزم جعل المستودع عامًا.

في المشروع والبيئة المطلوبين، أضف موردًا من Git ثم اختر استراتيجية بناء Docker Compose. اضبط:

| الحقل | القيمة |
|---|---|
| Base Directory | `/`، جذر المستودع |
| Docker Compose Location | `/compose.relay.yaml` |
| خدمة استقبال الدومين | `gateway` |
| منفذ الحاوية المستهدف | `8000` |
| البروتوكول العام | HTTPS |
| المسار | فارغ، دون بادئة |

اترك النشر المُدار المعتاد في Coolify؛ ملفنا لا يتضمن إعدادات وكيل مكتملة للنشر بوضع Raw. احفظ إعدادات المصدر وحمّل تعريف Compose. بحسب [توثيق Docker Compose الرسمي في Coolify](https://coolify.io/docs/applications/builds/docker-compose)، يشير مسار Compose إلى ملف داخل Base Directory، وتُحدد خدمة الدومين ومنفذها من إعدادات المورد.

في شاشة Domains اختر `gateway`، وHTTPS، والدومين، والمنفذ الداخلي 8000. إذا كان إصدار الواجهة يستعمل حقل URL واحدًا، تكون صيغة توجيه Coolify مثل `https://waraqstudio.jadallah.work:8000`؛ اللاحقة تختار منفذ الحاوية، بينما الهاتف يتصل بالدومين العام على 443. راجع [شرح Coolify للمنفذ الداخلي](https://coolify.io/docs/core/networking/domains#route-to-a-port-or-path).

**قيمة `PUBLIC_BASE_URL` تبقى `https://waraqstudio.jadallah.work` دون `:8000`.** لا تنسخ إليها صيغة توجيه Coolify التي تحتوي منفذ الحاوية.

ملف Compose يستخدم `expose: 8000`، ولا ينشر منافذ `gateway` أو `postgres` مباشرة على عنوان الخادم. لا تضف `ports:` لهما، ولا تمنح PostgreSQL دومينًا عامًا. يصل `gateway` إلى `postgres:5432` عبر شبكة Compose الداخلية.

صلاحية Git والدومين والشهادة واختيار الفرع إعدادات منصة للمرة الأولى. إن أردت التحديث عند كل دفع، فعّل Auto deploy في تكامل Git أو اضبط webhook المصدر وفق [دليل Coolify](https://coolify.io/docs/applications/deployments/automatic-deployments). لا يتطلب أي من ذلك كتابة رابط قاعدة البيانات يدويًا. النشر المباشر عند الدفع لا ينتظر تلقائيًا اختبارات GitHub؛ راجع نتيجة الالتزام قبل الاعتماد عليه، أو انشر الالتزام المقبول يدويًا.

## 3. متغيرات البيئة والأسرار

**للنشر الجديد في Coolify لا تكتب كلمة مرور قاعدة يدويًا.** عند تحميل التعريف يولّد Coolify المتغير `SERVICE_HEX_64_WARAQDB` بقيمة عشوائية من 64 حرفًا سداسيًا ويحفظها للمورد. يشير Compose إلى القيمة نفسها في PostgreSQL ورابط `DATABASE_URL` للتهيئة والبوابة، فتتطابق الاتصالات تلقائيًا. يدعم [Coolify المتغيرات المولدة وإعادة استخدامها](https://coolify.io/docs/applications/builds/docker-compose#generated-stack-values).

| المتغير | الإعداد في Coolify |
|---|---|
| `PUBLIC_BASE_URL` | يبدأ افتراضيًا بـ`https://waraqstudio.jadallah.work`؛ غيّره فقط إذا اخترت دومينًا آخر |
| `SERVICE_HEX_64_WARAQDB` | يولّده Coolify مرة واحدة ويحفظه؛ لا تستبدله أو تعِد توليده عند كل نشر |
| `DATABASE_URL` | يركّبه Compose داخل الخدمات؛ لا تضفه يدويًا في لوحة المورد |

`PUBLIC_BASE_URL` أصل HTTPS واحد، دون منفذ أو مسار أو معاملات أو `#` أو شرطة نهائية. استخدم الاسم نفسه في الهاتف وورق. لا تضبط `ALLOW_INSECURE_LOCAL_TEST` في الإنتاج. لا تنسخ قيم `.env.example` الوهمية إلى Coolify؛ الملف مخصص لتشغيل Compose خارج المنصة، حيث تحتاج إلى توفير المتغير بنفسك.

### ترقية مورد قديم له قاعدة موجودة

إذا نُشر الإصدار السابق باستخدام `POSTGRES_PASSWORD`، خذ نسخة احتياطية، ثم أنشئ في المورد **قبل تحميل Compose الجديد** متغير `SERVICE_HEX_64_WARAQDB` بقيمة كلمة مرور القاعدة القديمة نفسها. لا تسمح بتوليد قيمة مختلفة لقاعدة قائمة. بعد الترقية يشترك PostgreSQL والبوابة في هذا الاسم الجديد؛ لا تغيّر كلمة المرور لمجرد إعادة النشر.

تغيير متغير صورة PostgreSQL لا يغير اعتماد المستخدم داخل القاعدة الموجودة؛ تدوير كلمة المرور إجراء منسق بين القاعدة وإعداد المورد، وليس حلًا لتعطل الاتصال، ولا يستلزم حذف volume.

## 4. النشر والتحقق الأولي

اضغط Deploy، وانتظر اكتمال البناء وصحة الخدمتين. يبدأ المدخل بتهيئة مخطط قاعدة البيانات v1، ثم يشغل Uvicorn على `0.0.0.0:8000` بعملية واحدة. المخطط الأولي يُنشأ إن لم يوجد؛ هذا لا يمثل آلية لترحيل تغييرات مخططات مستقبلية معقدة.

**أبقِ عدد workers ونسخ gateway على 1.** خريطة اتصالات الأجهزة موجودة في ذاكرة هذه العملية؛ مضاعفة العمال أو النسخ تتطلب وسيط توجيه مشتركًا غير موجود في هذا الإصدار.

افتح من متصفح خارجي:

```text
https://waraqstudio.jadallah.work/internet
https://waraqstudio.jadallah.work/healthz
```

الثاني يعيد حالة `ok` عند نجاح فحص اتصال قاعدة البيانات. ومن طرفية خدمة `gateway` داخل Coolify يمكن تشغيل:

```bash
python -m deploy.relay.healthcheck
```

الفحص الداخلي يرسل Host الصحيح إلى `127.0.0.1:8000`. فتح الخدمة داخليًا باسم `localhost` دون هذا الترويس لا يمثل فحصًا صحيحًا لقائمة Host المسموح بها.

تحقق من ترقية `/ws/device` إلى WebSocket عبر HTTPS/WSS، ومن أن مهلة الوكيل تسمح باتصال طويل. لا تستبدل الاتصال الدوري بطلبات تُعيد تشغيل الأوامر؛ الورق يعيد الاتصال تلقائيًا دون إعادة إرسال أوامر التنفيذ القديمة.

## 5. تسجيل كل كمبيوتر على حدة

من طرفية **خدمة `gateway`** في Coolify، أنشئ رمزًا لهذا الكمبيوتر:

```bash
python -m relay enroll-code --minutes 10
```

الرمز عشوائي وأحادي الاستخدام، وينتهي بعد عشر دقائق. السطر الأول هو الرمز، والثاني وصف صلاحيته. لا تشاركه في السجلات أو المحادثات العامة. أنشئ رمزًا جديدًا لكل كمبيوتر؛ لا تعِد استخدام الرمز أو تنسخ ملفات الهوية بين الأجهزة.

على الكمبيوتر افتح ورق، ثم **الإعدادات ← الوصول من الهاتف · الإنترنت**. أدخل عنوان البوابة العام، واسمًا مميزًا لهذا الجهاز لا يتجاوز 120 حرفًا، ورمز التسجيل. اضغط **تسجيل هذا الجهاز** وانتظر حالة «متصل».

يحفظ اعتماد الجهاز في مخزن أسرار Windows. ملف هوية التطبيق لا يحتوي سرًا صالحًا وحده؛ نسخ مجلد البرنامج أو الإعدادات إلى جهاز آخر لا يمثل طريقة لتسجيله. عند تشغيل ورق لاحقًا اضغط **تفعيل اتصال الإنترنت**؛ الاتصال معطل عند بدء التطبيق حتى تفعله.

## 6. اقتران الهاتف واختيار الجهاز

1. على الكمبيوتر المطلوب اضغط **ربط هاتف جديد**.
2. امسح QR من الهاتف وافتح رابط البوابة، ثم أدخل اسم الهاتف.
3. قارن اسم الكمبيوتر ورمز المطابقة في الهاتف مع طلب الاقتران الظاهر في ورق.
4. على الكمبيوتر اضغط **موافقة على ربط هذا الهاتف**. قبل هذه الموافقة لا تُمنح صلاحية التحكم.
5. بعد الموافقة تظهر لوحة الجهاز. للربط بكمبيوتر آخر كرر الخطوات على ذلك الكمبيوتر ثم اختره صراحة من قائمة الأجهزة.

تذكرة QR صالحة خمس دقائق وأحادية الاستخدام. يحتوي جزء الرابط بعد `#` على التذكرة؛ يزيلها المتصفح بعد قراءتها. إذا انتهت الصلاحية أو استُخدمت التذكرة، أنشئ رابطًا جديدًا من ورق.

جلسة الهاتف تحفظ في Cookie آمنة `Secure` و`HttpOnly` و`SameSite=Strict`، بمدة قصوى 30 يومًا وحد خمول سبعة أيام. حذف بيانات الموقع أو استخدام متصفح آخر يتطلب اقترانًا جديدًا. لا توجد حسابات مستخدمين وكلمات مرور للهواتف في هذا الإصدار؛ منح الصلاحية يتم بالاقتران وموافقة الكمبيوتر.

## 7. الإيقاف وإلغاء الصلاحيات

لكل جهاز اقتران هاتف واحد فقط. حتى الطلب الموافق عليه الذي لم يجمعه الهاتف بعد يحجز مكانه مؤقتًا؛ لا يمكن منح موافقتين متعارضتين. لتغيير الهاتف ألغِ الحالي أولًا، ثم أنشئ QR جديدًا. المتصفح المختلف يُعد جلسة جديدة ولو كان على الهاتف نفسه. الاقتران المنتهي أو الخامل لا يحتفظ بالمكان إلى الأبد؛ يتطلب الربط التالي موافقة جديدة من الكمبيوتر.

- **إيقاف اتصال الإنترنت**: يوقف اتصال نسخة ورق الحالية. يستمر العمل المحلي؛ تبقى الهوية والاقترانات للاستعمال اللاحق.
- **تحديث الهواتف المقترنة ← إلغاء الربط**: يلغي صلاحية الهاتف على هذا الكمبيوتر فقط، ويقطع طلباته المعلقة. لا يلغي اقترانه بأجهزة أخرى.
- **إلغاء تسجيل هذا الجهاز**: يتطلب اتصال الجهاز بالبوابة. يلغي اعتماد الجهاز واقتراناته على الخادم، ثم يمسح الهوية المحلية بعد تأكيد الخادم. لإعادته تحتاج رمز تسجيل جديدًا.
- تسجيل الخروج من جهاز معين في الهاتف يلغي اقترانه بهذا الجهاز. تسجيل الخروج العام يلغي منح هذه الجلسة لجميع الأجهزة المقترنة بها.

لا تتعامل مع حذف ملف الهوية محليًا باعتباره إلغاءً على الخادم. لا توجد في CLI الحالية أداة لإلغاء جهاز غير متصل؛ عند الحاجة الطارئة أوقف البوابة من Coolify لمنع التحكم مؤقتًا، ثم نفذ معالجة إدارية مراجعة قبل إعادة الخدمة.

## 8. حدود التشغيل والثقة بالخادم

| البند | الحد الحالي |
|---|---|
| TXT المرفوع | حتى 20 ملفًا، بإجمالي 10 MiB من النصوص UTF-8 |
| غلاف JSON الكامل عبر WSS | 15 MiB |
| طلب JSON عادي غير رفع | 256 KiB |
| لقطات الحالة | محدودة بحجم رسالة 15 MiB؛ لا توجد صفحات تلقائية للقوائم الكبيرة |
| التنزيل الواحد | 100 MiB؛ دفعات حتى 64 KiB وبوابة ذات طابور محدود الذاكرة |
| الرفع المتزامن | عمليتان لكل جهاز، وأربع عمليات إجمالًا قبل قراءة أجسام الطلبات |
| مهلة الأمر / النقل | 30 ثانية / 60 ثانية |
| الجلسة / الخمول | 30 يومًا / 7 أيام |

الرفع في هذا الإصدار JSON/Base64 محدود الحجم، وليس رفعًا تدفقيًا كاملًا. حد التنزيل لا يضمن اكتمال 100 MiB عبر اتصال بطيء خلال 60 ثانية؛ ستتوقف العملية عند تجاوز المهلة. قد يضع CDN أو وكيلك حدًا أقل للحجم أو المهلة، فيلزم اختباره.

TLS يحمي النقل بين الهاتف والخادم وبين الخادم والكمبيوتر. مالك VPS والبوابة وسيطان موثوقان، ويمكن للخادم معالجة المحتوى المار به؛ هذا ليس تشفيرًا بين الطرفين E2EE. تحمي قاعدة البيانات الصلاحيات وبصمات الأسرار، لكنها بيانات حساسة يجب حماية نسخها الاحتياطية.

عند انقطاع الجهاز ترفض البوابة الأوامر فورًا ولا تخزنها لتشغيلها لاحقًا. إذا انقطع الاتصال بعد إرسال أمر، فقد يكون بدأ تنفيذه بالفعل؛ حدّث الحالة قبل تكراره، خصوصًا إعادة التفريغ المدفوعة. الإلغاء يوقف الطلبات التي لم تبدأ، ولا يعكس عملية أُنجزت محليًا.

## 9. النسخ الاحتياطي والاستعادة

عند ترقية بوابة قديمة تسمح بأكثر من هاتف للجهاز، تُضيف التهيئة فهرسًا فريدًا دون مسح المنح. إذا وجدت منحًا متعددة لجهاز واحد تتوقف برسالة واضحة بدل اختيار هاتف تلقائيًا. قبل هذه الترقية راجع المنح من النسخة السابقة وألغِ الزائدة صراحة، وخذ نسخة احتياطية؛ ثم أعد تشغيل الإصدار الجديد. النشر الجديد لا يحتاج إلى معالجة بيانات قديمة.

الـvolume المسمى منطقيًا `relay-db` يحفظ PostgreSQL بين النشرات. قد يضيف Coolify بادئة لاسمه الفعلي؛ راجع Persistent Storage قبل تغيير مورد أو مشروع. **التخزين الدائم ليس نسخة احتياطية**. لا تستخدم `docker compose down -v` أو حذف volume لعلاج عطل.

احفظ نسخة `pg_dump` دورية مشفرة خارج VPS، مع نسخة قبل التحديث والاستعادة. تحفظ القاعدة الهويات وبصمات الاعتمادات والاقترانات، ولا تحتوي ملفات الدروس. تحفظ أجهزة Windows أسرارها الخاصة بصورة مستقلة. صيغة `-Fc` مخصصة للاستعادة بواسطة `pg_restore` وفق [توثيق PostgreSQL 17 للنسخ](https://www.postgresql.org/docs/17/app-pgdump.html).

الأوامر التالية تُنفذ من SSH على VPS باستخدام shell لينكس، وليس PowerShell. حدد اسم حاوية PostgreSQL الفعلي من Coolify أو من:

```bash
docker ps --format '{{.Names}}  {{.Image}}'
```

استبدل قيمة المتغير باسم حاوية `postgres` الصحيحة لهذا المورد، واختر اسم ملف جديدًا لكل نسخة حتى لا تستبدل نسخة سابقة:

```bash
WARAQ_PG_CONTAINER='actual-postgres-container-name'
umask 077
mkdir -p /srv/waraq-backups
docker exec "$WARAQ_PG_CONTAINER" pg_dump -U waraq -d waraq -Fc > /srv/waraq-backups/waraq-2026-10-15-01.dump
```

تحقق من نجاح الأمر وأن الملف غير فارغ، ثم افحص فهرسه دون تعديل القاعدة:

```bash
docker exec -i "$WARAQ_PG_CONTAINER" pg_restore --list < /srv/waraq-backups/waraq-2026-10-15-01.dump
```

انقل النسخة إلى وجهة آمنة خارج الخادم. اختبار فهرس النسخة لا يغني عن تجربة الاستعادة على قاعدة منفصلة.

### الاستعادة دون حذف volume

1. أوقف `gateway` وحدها من Coolify، مع إبقاء `postgres` تعمل، حتى لا تتغير الاقترانات أثناء الاستعادة.
2. خذ نسخة جديدة من الحالة الحالية قبل أي استبدال، واختر نسخة الاستعادة الصحيحة وتأكد من توافق الإصدار.
3. الأمر التالي **يستبدل كائنات قاعدة `waraq` وبياناتها بمحتوى النسخة**. نفذه فقط بعد مراجعة الهدف والنسخة، وليس لفحص الاتصال:

```bash
docker exec -i "$WARAQ_PG_CONTAINER" pg_restore -U waraq -d waraq --clean --if-exists --no-owner --no-privileges --single-transaction < /srv/waraq-backups/waraq-2026-10-15-01.dump
```

4. إذا فشل الاسترجاع، راجع الخطأ قبل إعادة البوابة؛ لا تحذف volume. خيار `--single-transaction` يجعل الاستعادة تنجح كاملة أو تتراجع عند الخطأ، وفق [توثيق PostgreSQL 17 للاستعادة](https://www.postgresql.org/docs/17/app-pgrestore.html). عند نجاحه شغّل `gateway` واختبر الصحة وإعادة اتصال جهازين.
5. راجع الهواتف المقترنة والإلغاءات بعد الاستعادة: استعادة نسخة قديمة قد تعيد صلاحيات كانت أُلغيت لاحقًا، كما تفقد التسجيلات الأحدث من النسخة. ألغِ الصلاحيات غير المرغوبة من ورق، وأعد تسجيل الأجهزة التي لم تعد موجودة في القاعدة.

يمكن تنظيف تذاكر التسجيل والاقتران المنتهية دوريًا من طرفية `gateway`:

```bash
python -m relay prune
```

هذا الأمر ينظف التذاكر والطلبات المنتهية، ولا يمثل نسخة احتياطية أو إلغاءً شاملًا للأجهزة.

## 10. تشخيص الأعطال

| العرض | ما يجب التحقق منه |
|---|---|
| الدومين لا يفتح أو يعرض خدمة أخرى | DNS، تعارض الدومين، وارتباط الدومين بخدمة `gateway` ومنفذ 8000؛ راجع سجلات النشر والوكيل |
| `No Available Server` | صحة `gateway` و`postgres`، واكتمال بناء الصورة، ووجود متغيرات البيئة الصحيحة |
| رفض بدء الحاوية | كلمة مرور 64 hex، رابط PostgreSQL، وعدم تفعيل وضع الاختبار غير المشفر |
| 403 عند العنوان الصحيح | تطابق اسم الدومين تمامًا مع `PUBLIC_BASE_URL`؛ لا تستعمل عنوان IP أو اسمًا بديلًا أو مسارًا/منفذًا عامًا إضافيًا؛ تحقق أن الوكيل يحفظ Host |
| التسجيل يرفض الرمز | صلاحية الرمز وعدم استخدامه، عنوان البوابة وشهادة TLS؛ أنشئ رمزًا جديدًا من طرفية `gateway` |
| HTTP يعمل والجهاز لا يتصل | دعم WSS وترقية WebSocket في جميع الوكلاء، وشهادة الدومين، وسجلات البوابة وحالة اتصال الكمبيوتر |
| الهاتف يقول غير متصل | ورق مفتوح والكمبيوتر مستيقظ، واضغط تفعيل اتصال الإنترنت بعد تشغيل ورق؛ الخادم لا يوقظ الكمبيوتر |
| رفض اتصال مكرر | نسختان تحاولان استعمال هوية واحدة؛ أوقف النسخة الزائدة وسجّل كل كمبيوتر مستقلًا |
| QR لا يعمل أو تبقى الموافقة معلقة | أنشئ تذكرة جديدة، وافتحها في المتصفح المقصود، وراجع الطلب ورمز المطابقة على الكمبيوتر نفسه |
| 413 أو 503 أثناء الرفع | حد الحجم/الغلاف أو عدد عمليات الرفع؛ انتظر العمليات الجارية وقلل الملفات، ثم تحقق من حدود الوكيل |
| انقطاع التنزيل | استقرار الجهاز، حجم 100 MiB، مهلة 60 ثانية، وحدود الوكيل؛ أعد تنزيل الملف بعد التأكد من بقائه متاحًا |
| فشل PostgreSQL بعد تغيير كلمة المرور | عدم تطابق مستخدم القاعدة الموجودة مع المتغير الجديد؛ أعد ضبط الاعتماد بطريقة منسقة دون حذف البيانات |

سجلات وصول Uvicorn معطلة افتراضيًا لتقليل تسجيل الطلبات. لا تضف تسجيل أجسام الأوامر أو رؤوس Authorization أو رموز التسجيل أو Cookies. افحص أيضًا سياسات سجلات الوكيل وCDN اللذين تديرهما.

## 11. اختبار القبول قبل الاستخدام اليومي

- جرّب هاتفًا على بيانات الجوال وكمبيوترًا على شبكة أخرى؛ لا يكفي نجاح Wi-Fi المحلي.
- سجّل جهازين A وB برمزين مختلفين، واقترن بـA فقط. يجب أن يرى الهاتف A وحده، وأن ترفض البوابة استهداف B حتى لو عُدّل المعرّف في الرابط.
- اقترن بـB بخطوة مستقلة، ثم بدّل بين الجهازين وتحقق من الاسم والمهام. أوقف A وتأكد أن أوامره لا تُرسل إلى B.
- جرّب رفع TXT وتنزيل Word/TXT، وألغِ اقتران هاتف A وتأكد أن صلاحية B تبقى إذا كان مقترنًا به.
- أعد تشغيل البوابة دون حذف التخزين؛ يجب أن تبقى الاقترانات وأن تعيد الأجهزة المفعّلة الاتصال.
- اختبر استعادة نسخة احتياطية في بيئة منفصلة، ثم راجع الشهادة وتجديدها وحدود الوكيل قبل الاعتماد النهائي.

الاختبارات المحلية تغطي المصادقة والعزل والإلغاء والحدود واستمرار قاعدة SQLAlchemy على SQLite. يضيف `.github/workflows/relay.yml` بناء Docker وتشغيل PostgreSQL على Ubuntu، ويشترط مسار Release نجاحه قبل نشر المرفقات؛ لم يُشغّل هذا البناء محليًا لغياب Docker. راجع نتيجة GitHub Actions للالتزام المطلوب. نجاحها لا يثبت أن DNS أو Coolify أو النسخ الاحتياطية تعمل على VPS؛ تلك خطوات قبول النشر الفعلي.
